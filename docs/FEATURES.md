# 功能说明

按用户实际用到的顺序写，每条说清楚「什么条件下会怎样」。

## 故事与对话

**故事**是模板：标题、角色表、世界观、额外要求、开场白。**对话**是故事的一次具体演绎，开新局时把故事内容复制进来，之后两边各自独立。

两边的设定完全独立：建对话时把故事设定**快照**一份进来，之后各走各的。改故事只影响之后新开的局，已经开的对话纹丝不动；反过来，对话里加角色、改世界观、推剧情，也一个字都不会写回故事模板。要动故事设定，只在「故事」视图里改。

一局对话可以**分叉**：在任意一条消息上分出新时间线，新会话继承到那一刻为止的一切（消息、账本、摘要），原对话不动。

## 世界书

世界书是**按键触发**的补充设定：每条有关键词和正文，只有当最近几轮的正文里出现这些关键词时，那一条才被注入上下文。设定写得再多也不会稀释人设。

对话里攒出来的词条会自动进**这一局**的世界书。模型这一轮造出了值得记住的东西（地点、组织、规矩、物件、传闻），会在回复末尾补一行：

```
【新词条】{"keys":"触发词,别名","content":"一两句话说清它是什么"}
```

同一关键词只留一条，后写的覆盖前面的正文；这一局最多 40 条，满了不再加。这些词条**不会**写回故事模板。

想让它进下一局，在设定面板里点那条旁边的 `↑`，或者点底部的「这一局攒的条目存进故事设定」。只增不改：故事里已有同关键词的跳过，不会覆盖你写好的内容。

## 两种模式

| 模式 | AI 做什么 | 一句话一轮里可能出现的 |
| --- | --- | --- |
| 一般 | 叙述者，第三人称写场景与角色反应 | 一整段旁白 |
| 角色扮演 | 先旁白交代场面，再让在场角色各自发言 | 一段旁白 + 若干 `【角色名】` 段落 |

角色扮演是**圆桌式**：一轮里可以有好几个角色说话，但「不是每轮所有人都要说」，后面的人要接得住前面那个人那句。谁开口由模型按剧情判断，退场的人不会被叫到。

两种模式共用同一套状态行与账本。

## 角色

角色表存在 `sess.characters`，每项是 `{name, role, state, history}`。

**状态**（`state`）是模型每轮用 `【变化】` 维护的一句话，「此刻」是什么样。**历史**（`history`）是变化记录，最多留几条。角色卡弹层里只显示一条「状况」：`state` 当主句，后面最多附两条「此前：…」，不会重复。

**物品**不单列在顶栏，而是记在持有者名下：`status.items` 是 `{人名: "东西、东西"}`。点开某个角色的弹层才看得到他自己的物品；没署名的公共物品标「（公共）」。

**新角色怎么进的**：两条路，任一即可。

1. 模型写一行 `【新角色】名字：设定`（或 `【新角色】` 后跟 JSON）。
2. 状态行的「在场」名单里出现了一个陌生名字。

第 2 条是兜底：模型经常只在散文里写「己哭了」而不打标签，但它在写状态行时更容易把己算进在场。补登记用的就是这条。**名字必须真的出现在这两处之一**，只出现在正文里的名字不会被猜出来——启发式抽人名误判太多，没做。

角色数有上限（设置里可填 1~10，默认 4）。满了以后再出现新人，会记进 `pending_character` 并弹一个选择框让你决定换谁进来。

## 状态行与账本

模型每轮末尾写一行状态，格式固定：

    [[在场：甲,阿鸾|离场：周掌柜|地点：某酒馆|时间：深夜|关系：戒备|物品：甲=湿伞、铜钥匙；阿鸾=药包|目标：等他先开口|事实：钥匙到了甲手里]]

「在场 / 离场」决定角色的提示词分组和发言权；没写进离场的人默认还在场。「物品」按人写，用 `名字=东西`，几个人之间用 `；`。

**账本**（`facts`）记「发生过且不能反悔的事」，与状态互补：状态会被后来的覆盖，账本留存。新说法与旧说法相似度到 0.55 就把旧的标成 resolved 而不是删掉。

状态行写坏了有兜底：半截标签、裸 JSON、三反引号围栏、状态块前后的孤行都会被清掉，不让它漏进正文给人看见。

## 发送前冲突检查

发送前拿输入文本跟 `status.items` 对一遍：

- 提到某件东西，**主角名下也有** → 放行（他本来就拿着）。
- 提到某件东西，主角名下没有、但记在别人名下 → 输入框上方出黄色提示，列出**所有**持有者，可选「仍然发送」或「改一下」。
- 谁名下都没有 → 放行。

只认两个字符以上的物品名：单字的「伞」「刀」撞上普通用词的概率太高。`items` 若是旧格式（一串没有归属的公共物品），分不出归属，直接放行。

## 续写

模型写到一半停下是常事（字数到顶、自然停、被截断）。整条重写会换一个走向，而你往往只是想让它说完。

**最后一条**回复的操作栏有个 ▶：不新增消息，不推进轮次，把已写的半截当成待接的上文，
要求从最后一个字接着写、不重复、不重新开头、不加说明。新内容拼回原来那条，不是新增一条。

拼接时会切掉模型重复的尾巴（它很容易把上一句末尾重写一遍）。角色模式下按人合并：
同一个人继着说，就接在他自己那段后面，不会变成两个气泡。

只有最后一条能续写：往前接就不是同一轮了。想接更早的那句用分叉。

## 导入与导出

**导出**：顶栏的导出按钮存成 Markdown，带角色、状态、逐轮正文，给人看。

**导入**：侧栏对话栏的「⤓ 导入对话」选一份会话 JSON，换新 id 存进来。设定、角色、账本、
消息全带上，标题加「（导入）」。字段按白名单拷贝，文件里写多少字段都不会直接落到会话对象上。
没有 messages 的、或者根本不是对象的文件直接拒掉。导入的 Markdown 装不回来，只有 JSON 能。

### 测量数据层

上下文面板最下面三行：**写盘耗时、读盘耗时、会话文件大小**。

它们是拆不拆数据层的依据：现在都是 0～1ms、会话文件几十 KB，说明全量 JSON 读写
完全够用，拆 JSONL 或加 SQLite 只会引进一层错。**超过 100ms 再动手**，不凭感觉提前重构。

真到了那一天，顺序是先把 messages 拆成 append-only 的 JSONL，再考虚全文搜索建索引；不要一步到底。

## 上下文压缩

两个闸门，任一触发就压：上下文字数超过 `context_limit`，或消息条数超过当前档位的历史条数。

压缩把最早的一批消息交给模型写成摘要，累加进 `summary`，然后把游标 `compressed_upto` 往前推。**消息本身不删**——只推游标。这样分叉、回溯、导出都还能拿到全文。

保留区间从「压缩后保留最近消息数」起算，并且会对齐到一条 user 消息上，避免把一问一答切开。

压缩在后台线程里跑，不阻塞这次回复。

## 输入与滚动

**草稿**按会话存在 localStorage（`rp-draft:<会话 id>`），输入时 debounce 500ms 写入，进会话读回。发送成功后立刻清除——已发出的那句话在对话记录里，要重发点重试就行。清草稿时会顺手取消尚未执行的写入，否则输入后 500ms 内就发送会把旧文本写回去。

**滚动**只在离底部 80px 以内时跟随新内容。往上翻就停住，右下角浮出「↓ 新消息」，点一下回到底部。发消息、切会话、渲染完成这几处强制贴底。

## 全文搜索

顶栏 🔍 打开，输入至少两个字，扫 `data/` 下**所有会话**的正文、旁白和每段台词。结果给会话名、第几轮 / 共几条、前后 160 字片段。点结果切到那一局并滚到对应轮次，闪一下高亮。

不需要索引：几千条消息直接遍历 JSON 是毫秒级。

## 备份与存档点

**备份**把整个 `data/` 打成 zip 存进 `backups/`，打包时清空 `settings.json` 里的 API Key。可手动点，也可定时：每隔 N 分钟（5 ~ 20160）自动一次，最多留 M 份（1 ~ 30），超出的自动删最旧的。列表里的包可以直接还原，还原前会先自动存一份 `before-restore`。

**存档点**和备份不同：它是单个会话的 JSON 副本，触发点是每 15 轮一次和每次改设定前，每个会话留 10 份，回滚时整体替换。生成中会拒绝回滚，避免覆盖正在写的回合。

## 模型

支持本地 Ollama 和任意 OpenAI 兼容的云端接口。每个提供方可以配多个模型名，用逗号分隔；顶栏下拉切换。

「模型能力档位」是一张表（初级 / 标准 / 高级），同时决定上下文预算、历史条数、每条人设字数、账本条数、人设锚定频率和重试次数，详见 [CONFIG.md](CONFIG.md)。

温度由「创意」设置决定，不跟档位走：标准 0.75、创意 0.95、发散 1.1。这是角色性格的事，跟模型能力无关。
