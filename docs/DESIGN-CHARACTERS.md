# 角色与设定生成：改造方案

> 状态：待拍板，未动代码。本文只写设计，不含实现。

## 一、要解决的问题

三件事，都指向同一个毛病：**生成流程不看用户已经写过什么**。

1. **角色加不全**。开场白里站了三个人，角色表只有一个。四条加角色的路（模型回复带 `【新角色】`、状态行"在场"出现陌生名字、回流模板、手动填）全都要模型先开口；用户写在开场白、世界观里的人，代码从不读取。
2. **上限语义混了**。`max_characters` 一个参数同时管"模型现编的人"和"用户写死的人"。表满了，后者也被拒，于是剧情提到的人对不上号。
3. **生成会覆盖**。`buildSteps()` 无条件把 `world` 和 `opening` 放进生成队列。用户写得再完整，点一次「AI 帮我完善设定」也会被重写。

## 二、方案 A：认人（已实现，待并入流程）

点一次，模型读世界观、我扮演的角色、AI 角色、角色表、开场白、世界书，列出有名有姓的人，一人一行 `名字｜一句话设定`，解析后并入角色表。

已落地：`FIELD_TASKS["cast"]`、`parse_cast()`、`api_enhance` 返回 `data.cast`、设定面板的「👥 从设定里认出人物」按钮。

**并入流程后独立按钮撤掉**，改成一个勾选项，与其他项一次跑完。

## 三、方案 B：生成时自带名单

生成开场白和世界观时，让模型在正文末尾另起一行写 `角色：名字1、名字2`，只列这段里真正露面的人。保存时解析这一行、从正文里删掉、把名字收进角色表。

- 治的是**新写的内容**：以后 AI 生成的开场白，人自动进表。
- 治不了**手写的内容**：散文里的人名抽不出来，只能靠 A。
- 代价：生成结果多一行；要保证解析后从正文里剥干净，不能留在设定里。

## 四、方案 E：拆开上限语义

`max_characters` 只管**模型现编**的人；用户文本里出现的人**不受限**。

两种做法：

- **E1（推荐）**：`characters` 里全存，注入 prompt 时全给。现有 `role_chars` 上限（basic 200 / standard 400）已经在压字数，10 个角色也就几千字。删掉一处上限判断即可，代码量最少。
- **E2**：`characters` 全存，注入时只给"在场的 + 本轮被提到的"。省 token，但要多一套筛选逻辑，而且被筛掉的人模型下一轮又不认识了——把问题挪了个地方。

E1 的代价要说清：角色表没有硬上限，用户塞 30 个人进设定，prompt 就会被撑大。真出现这种情况再讨论，现在不值得为它写代码。

## 五、勾选式生成（核心交互）

`buildSteps()` 改成按勾选组装。勾选项：

```
☑ 我扮演的角色
☑ 角色卡（列出每一张，单独勾）
☑ 世界观
☑ 开场白
☑ 认出设定里的人物
```

**细项的 AI 按钮（`.field-ai`）保持原样**，单独重生某一项不走这个面板。两条路互不干扰。

### 勾选语义：已定用 X

用户的原话是「默认全选，取消开场白的勾就不生成开场白覆盖之前的」。这句话可以落到实处为三种不同行为：

**方案 X · 字面执行**
全选，勾了就生成，生成就覆盖。已有开场白会被重写，除非用户自己记得取消勾。
问题：这正是用户在抱怨的场景，默认值把他推到最容易出错的一侧。

**方案 Y · 已填的默认不勾**
只勾空着的项。已填的字段默认跳过，想重生成自己勾上。
省事，但"全选"变成了"部分选"，用户看到勾选状态会困惑：为什么我填过的没勾？

**方案 Z · 全选 + 覆盖开关（推荐）**
所有项默认勾上，底部单独一个「覆盖已经写好的内容」，**默认关**。

- 覆盖关（默认）：已填的项自动跳过，只生成空白的。用户填了完整开场白，直接点生成，开场白原样保留。
- 覆盖开：全按勾选跑，已填的也重写。

勾选状态始终如实反映"要生成哪些"，覆盖开关单独表达"允不允许重写已有内容"。两个概念分开，不会互相混淆。

**已定 X。** 理由：多数项只填了大概，本来就需要 AI 补全重写；只有个别项写得完整，手动取消那一两个的勾就行。X 的默认值符合这个主要用法。

配一个防护，避免误覆盖：勾了「覆盖已经写好的内容」的项目，生成结果先落在草稿里，状态栏列出"重写了哪几项"，保存前还能手动改回去。

cast 不设覆盖问题——它只往角色表里补人，不删人、不改已有角色的设定。

## 六、数据流

```
点「AI 帮我完善设定」
  → 读勾选 + 覆盖开关
  → buildSteps() 按勾选组装（跳过未勾的、跳过已有且未开覆盖的）
  → 逐项生成；cast 项拿到 data.cast 直接并入 draftChars
  → 开场白/世界观的结果里若有「角色：…」行，剥出来并入 draftChars
  → 全部跑完，用户手动微调
  → 点「保存」写入会话或故事模板
```

角色并入时**只补空设定，不覆盖用户写的**：已有角色缺 `role` 才填。

## 七、实施顺序

1. **E1**：删掉文本收人的上限判断。最小改动，先做。
2. **A 并入流程**：`cast` 作为一个 step，撤独立按钮，勾选面板接上。
3. **勾选面板**：`buildSteps` 按勾选组装 + 覆盖开关。这是用户感知最强的一块。
4. **B**：生成提示词加名单行 + 保存时解析剥离。

前两步纯后端，第三步入前端，第四步两端都动。每步都能单独验收，不会互相卡住。

## 八、风险

- **勾选面板改了 `buildSteps` 的组装逻辑**，`failedSteps` 那套"只补失败项"的重试机制要跟着改，否则重试会跑未勾选的项。
- **B 的名单行可能污染正文**：模型不一定老实另起一行，可能写进段落里。解析要保守——只在最后一行匹配 `^角色[：:]`，匹配不到就算了，不猜。
- **上限只管模型现编的人**（`upsert_character` 那条路）。`promote_characters` 已删：它会把对话里的人写回故事模板，跟「对话不改变故事设定」相冲。
- **覆盖开关默认关**，用户第一次点生成可能觉得"怎么没反应"——需要状态栏明确写出"跳过了 N 项已填内容"。

## 九、验收

- 设定里写满开场白和世界观，覆盖开关关着，点生成 → 这两项不被调用，原文一字不动。
- 勾上覆盖开关 → 两项被重写。
- 取消「认出设定里的人物」的勾 → 不跑 cast，角色表不变。
- 开场白里写三个人，角色表只有一个 → 点生成（cast 勾着）→ 三个人都在表里，且不受 `max_characters` 限制。
- 单张角色卡的 AI 按钮仍然只改那一张卡。
- 生成中途某项失败，再点一次只补失败的那项，不重跑已经成功的、也不跑未勾选的。
